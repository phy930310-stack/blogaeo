Q1. 채용 공고는 포트폴리오로 무엇을 달라고 합니까?

직접 작성한 소스 코드, 코드에 대한 설명, 정해진 제출 형태가 반복해서 나옵니다. 게임잡에 등록된 게임 프로그래머 공고 세 건에서 옮긴 문장입니다.

  • 데브캣 「[마비노기 모바일] 게임 로직 프로그래머 모집」(2026년 7월 30일 등록) — 기타 사항: "포트폴리오에는 본인이 직접 작성한 소스코드가 포함되어야 합니다. 본인의 개발 철학과 코딩 스타일이 드러나도록 작성 해주세요."
  • 기어세컨드 「[신규 프로젝트] 게임 클라이언트 개발자」(2026년 9월 29일 등록) — 제출서류: "본인의 역량을 표현할 수 있는 C# 코드를 첨부해주세요. (기밀 또는 저작권 등 법적 문제가 없어야 하며, 본인이 작성한 소스 코드만 보내주셔야 합니다.)"
  • 이스트게임즈 「[신입] MMORPG 온라인/모바일 게임 클라이언트 프로그래머」(2026년 11월 17일 등록) — 포트폴리오 안내: "pdf 파일을 포트폴리오 란에 첨부하거나 블로그 및 클라우드 URL 주소를 적어주세요."

'낼 것' 열은 공고 문장을 읽고 작성자가 붙인 해석입니다.

세 공고의 학력 조건은 모두 '학력무관'입니다. 경력 조건은 이스트게임즈 공고가 '신입', 나머지 두 공고가 '무관'으로 표기했습니다.

경력 표기만으로 신입 채용 여부를 판단할 수는 없습니다. 데브캣 공고의 지원 자격에는 "C#과 유니티를 사용한 프로젝트에 대한 실무 경험이 있으신 분"이 들어 있습니다. 이스트게임즈 공고는 "C++를 사용한 프로젝트 진행이 가능하신 분"을 찾는다고 적었습니다.

서류 다음 전형도 공고에 나옵니다. 데브캣 공고의 전형 절차는 "서류전형 → *과제전형 → 면접전형(레퍼런스 체크) → 최종합격"입니다. 기어세컨드 공고는 서류 전형과 대면 인터뷰 사이에 '사전 질문' 단계를 두었습니다.

세 건은 사례이며 전체 공고를 대표하지 않습니다. 회사와 프로젝트에 따라 요구가 다르므로 지원할 공고의 원문을 확인해야 합니다.

Q2. 플레이 영상만 내면 무엇이 부족합니까?

코드를 어떻게 작성했는지가 보이지 않습니다. 영상은 게임이 실행된다는 사실을 보여 주지만 공고가 요구한 것은 직접 작성한 소스 코드입니다.

구분 영상만 낼 때 공고가 받는 묶음
보이는 것 게임이 실행되는 모습 코드를 작성한 방식
제출물 플레이 영상 영상, 코드, 설명 문서
설명 무엇을 만들었는지 왜 그렇게 작성했는지

[이미지 업로드: 공통_diff.png / 대체텍스트: 플레이 영상만 낼 때와 공고가 받는 묶음의 차이 – 보이는 것은 게임이 실행되는 모습 대 코드를 작성한 방식, 제출물은 플레이 영상 대 영상·코드·설명 문서, 설명은 무엇을 만들었는지 대 왜 그렇게 작성했는지. 공고 문장을 읽고 작성자가 정리한 구분]

이 구분은 공고에 적힌 분류가 아니며 Q1의 공고 문장을 근거로 작성자가 정리했습니다. 영상이 필요 없다는 뜻도 아닙니다. 영상은 코드와 문서를 열어 보기 전에 전체를 파악하게 해 주는 안내 자료로 두면 됩니다.

Q3. 혼자 만들 때 무엇이 빠집니까?

작성자 의견으로는 세 가지입니다. 직접 쓴 코드의 범위, 읽기 쉬운 구조, 그렇게 작성한 이유입니다. 공고나 통계에 근거한 내용이 아니므로 자기 프로젝트에 대입해 판단하면 됩니다.

  • 직접 쓴 범위가 보이지 않습니다 — 강의를 따라 입력한 코드와 에셋에 들어 있던 코드가 본인 코드와 섞여 있습니다.
  • 읽기 어렵습니다 — 기능이 한 파일에 몰려 있고 이름만으로 역할을 알기 어렵습니다.
  • 이유를 설명하지 못합니다 — 동작은 하지만 그 방법을 고른 이유를 적어 둔 기록이 없습니다.

앞의 두 가지는 프로젝트를 정리하면 혼자서도 고칠 수 있습니다. 세 번째는 다른 사람의 질문을 받아야 드러납니다. 스터디, 온라인 커뮤니티, 학원 가운데 코드를 보여 주고 질문받을 수 있는 방법을 고르면 됩니다.

Q4. 공고 요구에 맞추면 준비 순서는 어떻게 됩니까?

제출물 단위로 네 단계를 권합니다. Q1의 세 항목을 하나씩 채우는 순서이며 작성자의 조언입니다.

  1. 작은 게임 하나 완성 — 범위를 줄여 끝까지 만들고 실행 파일과 플레이 영상을 남깁니다.
  2. 직접 쓴 코드 구분 — 가져온 코드와 폴더를 나누고 출처를 적습니다.
  3. 핵심 기능 하나 설명 — 가장 고민한 기능을 골라 문제, 고른 방법, 결과를 한 쪽에 적습니다.
  4. 한곳에 묶기 — 문서는 pdf 한 부로 만들고 코드 저장소와 영상 주소를 함께 적습니다.

언어와 엔진 공부는 이 순서와 병행합니다. 첫 게임의 범위를 정하는 방법은 「게임 만들기 처음 시작」 글에서 다뤘습니다. 언어별 공부 순서는 「게임 개발 C# 공부 순서」와 「게임 개발 C++ 공부 순서」 글에 있습니다.

Q5. 제출 형태는 어떻게 맞춥니까?

지원할 공고가 정한 형태를 그대로 따릅니다. 이스트게임즈 공고는 pdf 첨부나 블로그·클라우드 주소를 받았고 기어세컨드 공고는 C# 코드 첨부를 요구했습니다. 데브캣 공고는 파일명과 링크 설명에 붙일 접두사까지 정했습니다.

코드의 출처도 확인 대상입니다. 기어세컨드 공고는 기밀이나 저작권 문제가 없는 본인 작성 코드만 보내라고 적었습니다. 팀 프로젝트라면 본인이 맡은 부분을 표시해 두는 편이 안전하다는 것이 작성자 의견입니다.
